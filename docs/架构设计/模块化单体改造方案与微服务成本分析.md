> 关联分支：`fix/tcp-heartbeat-and-test-harness`

## 一、现状诊断

### 1.1 当前形态：伪微服务（分布式单体）

| 维度 | 事实 | 判断 |
|------|------|------|
| 模块拆分 | 12 个 Maven 模块，各自独立 `@SpringBootApplication` | ✅ 物理边界存在 |
| 跨模块调用 | message 直接 import 并注入 user/friendship/conversation 的 **domain service**（3 处） | ❌ 边界违规 |
| 跨模块调用 | 4 个模块已有 **Feign 客户端**（friendship→user、group→message、message→group、user→group） | ⚠️ 两套机制并存 |
| 数据库 | 11 个服务**共享同一个 `vela` 库**（3307；message-store 3306 同库名） | ❌ 数据无隔离 |
| 组件扫描 | `MessageApplication` 的 `scanBasePackages`/`MapperScan` 跨包扫描 conversation/user/friendship | ❌ 边界违规 |
| 共享层 | `service-common` 混入 entity/mapper（`ImGroupEntity`、`ImFriendShipEntity`、`ImGroupMessageHistoryMapper`） | ❌ 归属不清 |
| 部署 | docker-compose.yml 已编排 12 个业务容器 + SkyWalking/Prometheus/Grafana/ELK | ⚠️ 按伪微服务写了编排 |
| 注册发现 | 仅 vela-tcp 用 ZK 注册；业务服务间 Feign 未接注册中心（无服务发现） | ❌ 缺核心件 |

**结论**：拆了壳、没拆核——业务服务间实际是进程内 Bean 互调 + 共享库，却部署 12 个进程，同时背上
Feign 网络调用和直接 import 两套机制。这是"分布式单体"：**付微服务的部署成本，拿不到隔离收益**。

### 1.2 关键判断

- 本地开发/联调要起 12 个进程 + 全套中间件，30+ 启动坑的排查范围 = 12 个应用
- 零自动化测试（本次已补 vela-tcp 4 例），架构改动无护栏
- "微服务化"只完成了**物理分层**，未完成**调用边界**和**数据边界**

## 二、模块化单体目标架构

### 2.1 部署形态：3 个进程（当前 12 个进程 → 3 个）

```
┌──────────────────────────────────────────────────────────┐
│ 部署单元 1：vela-tcp（接入层 · 独立）                       │
│ Netty 长连接网关 · config.yml · Redis/MQ/ZK · 独立调优      │
└──────────────────────┬───────────────────────────────────┘
                       │ MQ
┌──────────────────────┴───────────────────────────────────┐
│ 部署单元 2：vela-gateway（接入层 · 独立）                   │
│ HTTP/REST 网关                                            │
└──────────────────────┬───────────────────────────────────┘
                       │ MQ
┌──────────────────────┴───────────────────────────────────┐
│ 部署单元 3：vela-business（业务域 · 合并为 1 个进程）        │
│  service-user / friendship / group / conversation /       │
│  message / bot / admin / config / office / knowledge /    │
│  message-store                                            │
│  模块间调用 = 进程内接口注入（去 HTTP 化，见 2.4）           │
│  共享 MySQL vela 库（表按域前缀隔离，见 2.3）               │
└───────────────────────────────────────────────────────────┘
```

**为什么不是单进程**：TCP 网关是长连接资源密集（线程模型/心跳/编解码调优），与业务（IO/DB 密集）
混跑互相拖累；HTTP 网关同理。接入层独立、业务域合并是网关型系统的常见平衡。

**重要澄清：部署单元 ≠ 单实例。** 3 个部署单元是构建/发布单元，业务进程建议运行 **≥2 实例 + 负载均衡**
（实例无状态：session 在 Redis、模块间走 MQ）。实例级故障模型与微服务多实例完全一致——
进程崩溃时"全挂"只发生在只部署 1 个实例时。详细故障模型见 2.6。

### 2.2 模块边界与依赖规则

每个业务域保持独立 Maven 模块（编译期隔离 = 防循环依赖的硬墙），内部四层：

```
vela-service-message/
├── interfaces/        # Controller、MQ 消费者入口、Feign 接口（见 2.4）
├── application/       # 用例编排 ★ 跨模块调用唯一允许点
├── domain/            # 纯业务逻辑，不 import 任何其他模块的 domain
└── infrastructure/    # MyBatis-Plus/Redis 实现，实现 domain 接口
```

| 规则 | 允许 | 禁止 |
|------|------|------|
| 调用方向 | application → 对方 application 接口 | domain ↔ domain 互调（现状违规） |
| 数据访问 | 域内 infrastructure 读写**自己的表** | 跨域直接读写对方表 |
| 通信方式 | 进程内接口注入 + MQ 异步 | 模块间 HTTP 直连（去 Feign 网络化） |
| 共享内容 | service-common 只放纯值对象/工具/常量 | service-common 放 entity/mapper（现状违规） |

### 2.3 共享库的域隔离设计

数据库保持一个 `vela` 库（模块化单体允许），但建立**逻辑隔离纪律**：

| 域 | 表前缀（示例） | 唯一访问者 |
|----|----------------|-----------|
| user | `user_*`、`im_user_*` | service-user.infrastructure |
| friendship | `friend_*`、`im_friend_*` | service-friendship.infrastructure |
| group | `group_*`、`im_group_*` | service-group.infrastructure |
| message | `msg_*`、`im_message_*` | service-message.infrastructure |
| conversation | `conversation_*` | service-conversation.infrastructure |

- 跨域读写必须走对方模块 application 层接口（进程内），禁止直连对方表
- 事务：域内 `@Transactional` 为主；跨域写操作走 MQ 最终一致（现状 MQ 链路已具备）
- 归位：`service-common` 中的 entity/mapper 迁回所属域模块

### 2.4 已有 Feign 客户端的处理策略（关键设计决策）

现状 4 个 Feign 客户端（friendship→user、group→message、message→group、user→group）**保留接口，
换实现**——"缝保留法"：

```
改造前（伪微服务）：调用方 → @FeignClient 代理 → HTTP → 对方服务
改造后（模块化单体）：调用方 → 同一接口 → 本地 @Service 实现（进程内 Bean）
将来拆微服务：       调用方 → 同一接口 → 换回 Feign 代理 → HTTP
```

- 接口定义留在 `interfaces/feign/`（归属调用方），模块化单体阶段用 `@Service` 本地实现注入
- 调用方代码**零改动**；将来拆微服务时把实现换回 Feign 代理即可——这就是"缝"
- 收益：去掉模块间 HTTP 往返（同进程走网络栈是纯浪费），又不破坏接口契约

### 2.5 边界保障：ArchUnit 架构测试

模块化单体最大的风险是边界随时间腐烂。用测试锁死（接 CI）：

```java
// 示例断言（ArchUnit，JUnit 5）
noClasses().that().resideInAPackage("..message.domain..")
    .should().dependOnClassesThat().resideInAnyPackage("..user..", "..friendship..", "..conversation..");

noClasses().that().resideInAnyPackage("..domain..", "..infrastructure..")
    .should().dependOnClassesThat().resideInAPackage("..service.common.entity..");
```

- 架构约束从"文档"变成"CI 必过的测试"
- 依赖层面：各模块 pom 收敛，service-common 不再是"垃圾场"

### 2.6 故障模型与爆炸半径应对

**核心担忧**：所有业务集中于一个部署节点，挂了全影响（单点故障）。

**故障类型拆解**（模块化单体 vs 微服务）：

| 故障类型 | 模块化单体（1 实例） | 模块化单体（N 实例+LB） | 真微服务（独立库） |
|----------|----------------------|-------------------------|--------------------|
| 进程崩溃（bug/OOM/死锁） | 全部业务停 | 单实例挂，LB 摘除 | 仅该服务挂 |
| 资源耗尽（流量洪峰） | 一个域拖垮全部 | 单实例挂 | 仅该服务 |
| 基础设施故障（DB/Redis/MQ 挂） | 全挂 | 全挂 | **同样全挂**（共享中间件集群；分库后才隔离） |
| 部署/配置事故 | 一次发布全局生效 | 灰度/回滚到实例 | 按服务灰度/回滚 |
| 网络分区 | 无跨进程调用，不涉及 | 实例无状态，无影响 | 服务间调用失败，需重试/熔断 |

**结论**：

1. 进程崩溃/资源耗尽/部署事故是模块化单体的真实弱点（爆炸半径 = 整个业务进程）；
2. **基础设施故障微服务也躲不掉**——Vela 现状 11 服务共享一个 MySQL，真微服务化拆库前，DB 挂了照样
   全挂。**真正的单点是中间件，不是进程**；高可用预算应优先投给 MySQL 主从/Redis 集群/MQ 集群。

**缓解措施**：

| # | 措施 | 说明 |
|---|------|------|
| 1 | 多实例 + LB | 业务进程 ≥2 实例，实例无状态化（session 在 Redis ✅；@Scheduled 加分布式锁防重复） |
| 2 | 进程内资源隔离 | 各域独立线程池 + 连接池配额，防一个域耗尽 JVM 资源拖垮全部 |
| 3 | 域级降级开关 | `ServiceDegradationManager` 已存在，按域配置降级/熔断 |
| 4 | 优雅停机 + 健康检查 + 自动重启 | 容器平台层面（K8s/docker restart policy） |
| 5 | 灰度发布 + 快速回滚 | CI/CD 自动化补偿单进程发布窗口风险 |
| 6 | 中间件高可用 | MySQL 主从、Redis 集群、MQ 集群——优先于进程拆分投入 |

**务实折中：按爆炸半径敏感度分 2-3 个业务进程**（模块化单体家族，共享库 + 进程内调用不变）：

```
vela-business-core（核心链路 · 多实例）：user/friendship/group/conversation/message/message-store
vela-business-mgmt（管理链路 · 低频）：bot/admin/config/office/knowledge
```

- 核心链路挂了不影响管理功能（反之亦然），爆炸半径从"全部业务"缩到"核心"或"管理"其一
- 仍未付出微服务的网络/运维成本；将来某域要独立扩容，本就是独立 Maven 模块，切出即可
- **爆炸半径是可配置的光谱**：全业务单进程 → 按域分组多进程 → 真微服务，按需取位置

## 三、真微服务改造成本分析

### 3.1 已具备（零增量成本）

| 资产 | 现状 |
|------|------|
| 模块物理拆分 | 12 个 Maven 模块 + 独立启动类 |
| 部分 Feign 化 | 4 个 Feign 客户端（friendship→user、group→message、message→group、user→group） |
| MQ 链路 | 网关→业务、业务→message-store |
| 容器编排 | docker-compose 已编排 12 业务容器 + SkyWalking/Prometheus/Grafana/ELK |
| 链路透传 | TraceIdContext + MQ header + Feign interceptor |
| 注册（部分） | vela-tcp 走 ZK 注册 |
| 依赖版本 | pom dependencyManagement 已声明 Sentinel 1.8.6（未实际引入） |

### 3.2 需改造项成本清单（按单人全职估算）

| # | 改造项 | 现状 | 主要工作 | 估算 |
|---|--------|------|----------|------|
| 1 | **数据拆分**（最大头） | 11 服务共享 1 个 `vela` 库 | 每域独立库：DDL 拆分、mapper 数据源隔离、跨库事务改 MQ 最终一致、存量数据迁移 + 校验 | 1-2 周 |
| 2 | 调用边界全覆盖 | message 3 处 domain 直调 + 部分 Feign 并存 | 全部收敛为接口/Feign；domain 层零跨模块 import | 3-5 天 |
| 3 | 服务发现 + 负载均衡 | 业务服务无注册中心，Feign 无 LB | 引入 Nacos/Consul + spring-cloud-loadbalancer，改造 Feign url | 2-3 天 |
| 4 | 配置中心 | 12 份 application.yml | 迁 Nacos Config，按服务拆分配置与环境隔离 | 1-2 天 |
| 5 | 分布式事务/一致性 | 共享库时可跨模块事务 | 拆库后跨域写全走 MQ 最终一致：补偿/对账机制；评估 MessageLockManager、ServiceDegradationManager、PendingAckTracker | 1-2 周 |
| 6 | 熔断限流 | Sentinel 声明未用 | 引入 sentinel-annotation-aspectj，发消息/Feign 调用等关键链路加规则 | 1-2 天 |
| 7 | 可观测性打通 | SkyWalking/Prometheus 已编排但业务未接入 | agent 接入、micrometer 指标暴露、TraceId 全链路验证 | 2-3 天 |
| 8 | CI/CD | 无流水线 | 12 服务独立构建/发布流水线、镜像仓库、环境部署 | 2-3 天 |
| 9 | 测试体系 | vela-tcp 4 例 | 每服务 ContextLoadTest + 跨服务契约测试（否则联调地狱） | 3-5 天 |
| 10 | 运维/排障 | 无 | 12 容器日志聚合、告警、容量规划、故障演练 | 持续 |

**总量：约 4-8 周**。且每一项都是"运行时可错"的（30+ 启动坑的教训重演风险），
要求测试护栏先行，否则每个服务的每次启动都可能踩坑。

### 3.3 隐性成本

- **联调复杂度**：跨服务问题跨进程定位，依赖日志/链路追踪
- **契约管理**：接口变更需契约测试，否则服务间互相踩
- **心智负担**：12 个服务的配置、版本、发布窗口管理
- **数据不可逆**：拆库一旦执行难以回退，是决策成本最高的一步

## 四、对比决策矩阵与推荐

| 维度 | 模块化单体（推荐） | 真微服务 |
|------|--------------------|----------|
| 改造工作量 | ~1 周（3 阶段） | 4-8 周（10 项） |
| 改造风险 | 合并期 Bean/Mapper 冲突（一次性、早暴露） | 数据拆分、分布式事务、联调地狱 |
| 收益兑现 | 立即：部署 12→3 进程、测试集中、本地起 1 进程 | 独立扩缩容/独立发布/故障隔离 |
| 当前需求匹配 | ✅ 单人/单团队/无独立扩缩容需求 | ❌ 无 |
| 可回滚性 | 高（代码重构为主） | 低（数据拆分不可逆） |
| 将来升级 | 边界已划好，按缝切 Feign + 拆库即可 | — |

**推荐：模块化单体先行。** 理由：

1. 当前无独立扩缩容/发布需求，微服务的核心收益兑现不了；
2. 微服务成本大头是数据拆分（1-2 周）和分布式事务（1-2 周），现在付是纯支出；
3. 模块化单体的边界工作（域隔离、entity 归位、调用收敛）与微服务前置工作 **100% 重叠**，等于为将来存钱；
4. "缝保留法"（2.4）让将来拆服务只需"换实现 + 拆库"，无需推倒重来。

**升级触发条件（出现任一信号再动）**：

- 某域流量独大，需要独立扩容
- 出现独立发布节奏或多团队协作
- 数据隔离出现合规要求

届时按已划好的边界逐个切：先切 message（调用最复杂），再切 user（被依赖最多），其余按依赖顺序推进。
