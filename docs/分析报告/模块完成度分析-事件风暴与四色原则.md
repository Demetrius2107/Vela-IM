## 二、四色原型识别（领域模型完整度）

四色原型四要素：**MI（时刻段/事件记录）、Role（角色）、PPT（参与方/地点/物品）、Desc（描述/目录）**。领域模型成熟度 = 四色要素覆盖度 + 事件驱动程度。

### 2.1 message（消息域）—— 四色覆盖最全 ⭐

| 四色 | 实例 |
|------|------|
| MI | ImMessageHistoryEntity、ImMessageReadEntity、ImMessageFavoriteEntity（发送/已读/收藏即时刻段事件） |
| Role | 发送方/接收方（MessageReadedContent）、RecallStrategy 多态（P2P/Group 角色策略） |
| PPT | ImMessageBodyEntity、ImFileEntity、ImStickerEntity |
| Desc | ImStickerPackEntity（贴纸包目录） |

- **事件驱动**：✅ MQ 消费（ChatOperateReceiver）+ pipeline（Validate→RateLimit→Dedup→PersistAndPush）+ 补偿调度（MessageCompensationScheduler）
- **业务规则**：限流、去重、发送前校验（CheckSendMessageService：禁言/禁发/好友关系/群权限）、撤回策略（策略模式）、补偿重试
- **结论**：**非 CRUD，IM 核心业务逻辑完整**。领域事件链：发送→校验→限流→去重→持久化→推送→已读→撤回→补偿，闭环。

### 2.2 group（群组域）—— 业务规则密集 ⭐

| 四色 | 实例 |
|------|------|
| MI | ImGroupMemberEntity、ImGroupPollVoteEntity、ImGroupAnnouncementReadEntity |
| Role | 群主/管理员/成员（GetRoleInGroupResp）、群聊角色权限校验 |
| PPT | ImGroupEntity、ImGroupFileEntity、ImGroupAnnouncementEntity |
| Desc | ImGroupTagEntity + ImGroupTagMappingEntity（标签体系） |

- **事件驱动**：✅ MQ 消费（GroupChatOperateReceiver）+ GroupBroadcastNode/GroupValidateNode 管道
- **业务规则**：成员角色权限（禁言豁免管理员）、群聊广播（写扩散+离线）、投票/公告/标签/文件完整子域
- **结论**：**非 CRUD**，群生命周期（创建/解散/转让/成员管理/禁言/投票）齐全。

### 2.3 conversation（会话域）—— 四色单薄 ⚠️

| 四色 | 实例 |
|------|------|
| MI | 无独立事件记录（仅操作触发落库） |
| Role | 无角色概念 |
| PPT | ImConversationSetEntity（仅 1 实体） |
| Desc | 无 |

- REST 仅 4 端点（convertConversationId / messageMarkRead / delete / update / sync）
- **结论**：**接近纯 CRUD**，会话域只有"集合记录 + 已读落库"，缺会话排序、置顶、免打扰、会话归档等业务语义。

### 2.4 user（用户域）—— 中等 ⭐

| 四色 | 实例 |
|------|------|
| MI | UserStatusChangeNotifyContent（状态变更事件） |
| Role | 在线/离线状态角色（ImUserStatusService） |
| PPT | ImUserDataEntity |
| Desc | 无独立目录 |

- 事件驱动：✅ MQ（UserOnlineStatusReceiver 订阅状态变更）
- **结论**：用户 CRUD + 在线状态推送 + 状态订阅，**半 CRUD**；缺资料审核、实名等强业务。

### 2.5 friendship（好友域）—— 业务完整 ⭐

| 四色 | 实例 |
|------|------|
| MI | ImFriendShipRequestEntity（好友申请=时刻段事件） |
| Role | 申请方/被申请方、好友分组角色 |
| PPT | ImFriendShipEntity |
| Desc | ImFriendShipGroupEntity（分组目录） |

- 业务规则：申请→审批流程、双向好友校验、黑名单（checkFriendStatus）、分组管理
- **结论**：**非 CRUD**，好友全生命周期（申请/审批/分组/黑名单）完整。

### 2.6 bot（机器人域）—— 业务模式完整但功能浅 ⭐

| 四色 | 实例 |
|------|------|
| MI | BotMessageRelayService（消息中继） |
| Role | 命令处理角色（BotCommandRegistry + 命令多态 Echo/Help/Ping） |
| PPT | ImBotEntity、ImUserBotEntity |
| Desc | BotMarketService（机器人市场目录） |

- **结论**：架构模式好（命令注册/分发/策略），但**业务功能浅**——命令仅 echo/help/ping，缺真实业务机器人场景。

### 2.7 admin（管理域）—— 聚合查询型 ⚠️

| 四色 | 实例 |
|------|------|
| MI | AdminLoginLogEntity、AdminOperationLogEntity（审计日志） |
| Role | AdminUserEntity、AdminRoleConfig |
| PPT | 跨模块聚合（用户/群/消息） |
| Desc | SystemConfigEntity |

- **结论**：**半 CRUD + 聚合查询**，AdminService 跨 user/message/group/bot 做运营大盘查询；有认证（AdminAuthService）与审计日志。

### 2.8 config（配置域）—— 纯 CRUD ⚠️

| 四色 | 实例 |
|------|------|
| PPT | FeatureFlagEntity、UserConfigEntity |
| Desc | 无独立目录 |

- **结论**：**接近纯 CRUD**（开关 + 用户配置 KV），FeatureFlagService 有启动落库默认值逻辑，但无业务事件/状态机。

### 2.9 office（办公域）—— CRUD 倾向 ⚠️

| 四色 | 实例 |
|------|------|
| MI | ApprovalEntity（审批=时刻段事件） |
| Role | 无显式角色 |
| PPT | ScheduleEntity、TodoEntity |
| Desc | 无 |

- **结论**：**半 CRUD**，审批/日程/待办三件套，审批缺少多级审批/会签/审批链等业务语义。

### 2.10 knowledge（知识库域）—— 业务最丰富 ⭐⭐

| 四色 | 实例 |
|------|------|
| MI | DocVersionEntity（版本历史）、DocReadEntity（阅读统计）、DocFavoriteEntity、DocApprovalEntity |
| Role | owner/editor/reader 文档权限角色（PermissionService） |
| PPT | DocumentEntity、DocVectorEntity |
| Desc | CategoryEntity（分类目录树） |

- **业务规则**：发布审批**状态机**（DRAFT→PENDING→PUBLISHED/REJECTED，驳回必填原因）、版本 diff 检测与 50 版容量保护、软删除+回收站级联、向量检索 RAG（可插拔 Embedding/VectorStore/RagAnswerer）、TF 抽取式摘要、FAQ 热榜加权
- **结论**：**完全非 CRUD**，全项目业务逻辑最完整的模块。

## 三、业务逻辑缺失点（事件风暴视角）

| 模块 | 缺失/薄弱 | 优先级 |
|------|-----------|--------|
| conversation | 会话排序/置顶/免打扰/归档、会话已读聚合 | P1（IM 体验缺失） |
| user | 多端登录会话管理、资料修改审核 | P2 |
| group | @全体成员、群聊消息漫游/增量同步 | P2 |
| message | 撤回时间窗限制（有策略但未见超时窗口校验）、消息漫游 | P2 |
| office | 多级审批/会签、审批流配置化 | P2 |
| bot | 真实业务机器人（当前仅 echo/help/ping 演示） | P3 |
| config | 配置版本化/灰度发布 | P3 |

## 四、总结：完成度分级

| 级别 | 模块 | 判定 |
|------|------|------|
| ⭐⭐ 业务完整 | **knowledge** | 状态机+版本+RBAC+RAG+摘要+热榜，四色全覆盖 |
| ⭐ 业务完整 | **message / group / friendship** | 事件驱动+pipeline+业务规则闭环 |
| ⭐ 半 CRUD | **user / admin / office / bot** | 有业务逻辑但部分子域为 CRUD 或功能浅 |
| ⚠️ 纯 CRUD | **conversation / config** | 基本为增删改查，缺领域事件与业务语义 |

**总体结论**：
1. 核心 IM 链路（消息/群/好友）**不是纯 CRUD**，已有事件驱动与业务规则，此前"是否只是 CRUD"的担忧在核心域不成立；
2. 薄弱点在 **conversation（会话）与 config（配置）**——建议下一步优先补会话域业务语义（置顶/免打扰/排序）；
3. knowledge 模块是全项目业务建模的标杆（状态机+四色完整），可作为其余模块演进参照。
